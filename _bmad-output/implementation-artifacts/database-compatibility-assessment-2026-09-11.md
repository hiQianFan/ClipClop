# ClipClop 数据库兼容与恢复评估

日期：2026-09-11。代码基线：`e4bc0df`，应用代码 0.11.1，数据库 schema 9。范围：评估及研究，不修改应用实现、不操作正式数据库、不隔离 dev 与正式版。

## 结论

采用**明确的最低兼容版本、顺序原子迁移、迁移前一致性备份、可见的启动失败处理**。允许经过约定和验证的旧程序使用新版数据库，不能承诺任意旧程序都能打开任意新数据库。

兼容性必须同时覆盖 SQL 结构、记录值、设置格式和业务行为。检查“多了哪些字段”或“SQL 能不能执行”都不足以证明安全。

这次 schema 8 → 9 增加可空收藏字段，在 SQL 层面是增量变更；但旧版自动清理及清空历史不保护收藏，因此不是完整的业务兼容。不能把 0.10.0 的版本检查删除就算修好。

推荐先发布一个完整的兼容机制基线版本，此后普通可选字段的增加不再阻止该基线版本运行；遇到删除规则、内容类型、必填约束等真正不兼容变化时，提高最低兼容版本。已经安装的 0.10.0 必须更新，无法事后获得它没有实现的兼容协议。

## 1. 本项目已经确认的事实

| 位置 | 现状 | 判断 |
| --- | --- | --- |
| `src-tauri/src/storage/migrations.rs:11` | 只接受 0、4～9；不认识的版本一律返回删库提示 | 更高版本不等于不兼容；错误文案不适用于正式用户数据 |
| 同文件的新库分支 | 执行建表 SQL 后另写 `user_version`，没有包裹事务 | 中断可留下有表但版本为 0 的半初始化数据库 |
| 同文件的历史迁移 | 每步事务内改变数据并更新版本；下一步另开事务 | 每步原子性已有；整次升级不原子，失败后可能停在中间合法版本。不能误称所有迁移都无事务 |
| `storage/database.rs:36` | 兼容判定前设置持久化 WAL 模式 | 应在识别数据库后再做持久化配置，避免拒绝启动前已经改变数据库模式 |
| `storage/database.rs:80` 等 | 读写列名明确，局部 UPDATE，不是整行 REPLACE | 保留未知普通列的基础已经存在，应继续复用 |
| `storage/database.rs:288`、`:348` | 新版清理和清空排除收藏 | 0.10.0 对应 SQL 没有条件；放行旧版后收藏可能被自动删除 |
| `workflows/capture.rs` | 捕获成功后执行保留策略 | 旧版删除风险不需要用户主动点击“清空”就会触发 |
| `settings/model.rs` | 当前版与 0.10.0 都有 `serde(flatten)` 的 `extra`，并有往返测试 | 纠正前次评估：不能说普通设置读写必然丢未知字段 |
| `settings/service.rs:33` | 保存表单用传入 Settings 替换原对象，只特殊保留两个更新字段 | 旧快照缺少或携带旧的 extra 时，仍可覆盖最新 extra；正常 UI 展开对象会携带 extra，不能把条件性风险说成已发生的数据丢失 |
| `settings/model.rs` 与 `lib.rs:148` | 部分设置字段必填，枚举严格；启动直接反序列化整个对象 | 缺失 language 或未来枚举值可导致启动失败，现有测试甚至要求 language 严格失败 |
| `history/model.rs:31`、`storage/database.rs:431` | 未知内容类型、坏时间或 metadata JSON 的解析失败向上传播 | 一条不能解析的记录可能让整页查询失败；新增列兼容并不解决这一层 |
| `storage/settings.rs:30` | 读改写由进程内连接 Mutex 保护，没有 SQL 事务覆盖整个过程 | 当前单进程内互斥有效；不能据此宣称跨进程原子 |
| `lib.rs:92` | 已安装 single-instance 插件，早于应用 setup | 不需要再造唤醒已有实例的机制，但它不等于严格的数据目录锁 |
| 本地 single-instance 2.4.2 macOS 实现 | socket 监听/通知某些失败情况下继续启动 | 同目录并发保护需补强，不能依赖 SQLite 文件不损坏就推导业务不会冲突 |
| 本地 rusqlite 0.37.0 | 默认 busy timeout 为 5000ms | 已有锁等待；不应把没有显式设置误报为完全没有超时 |
| 存储及启动代码 | 未发现数据库迁移前备份或恢复流程 | 失败后的用户恢复能力不足 |
| `lib.rs` setup | 数据库/设置失败向 Tauri setup 传播 | 实际日志证明此路径发生 panic 并 abort；只替换最终 `.expect` 无法修复 setup 内的 abort |

另外，旧 schema 的 `content_type` CHECK 包含 `code`；7→8 只更新值，没有重建 CHECK。升级库和新建库结构存在合法历史差异。现有部分迁移测试从当前 schema 删除几行生成“旧库”，无法充分覆盖这些差异。后续结构检查应校验所需能力，不能直接对整个建表 SQL 做字符串相等比较。

## 2. 其他软件如何处理

### Chromium：迁移版本与兼容版本分开

Chromium 的 `MetaTable` 同时维护数据库版本与最低兼容版本。官方源代码用“增加可选列”说明：迁移版本可以增加，而兼容版本保持不变；HistoryDatabase 则检查最低兼容版本，过高时返回 `INIT_TOO_NEW`。[MetaTable 源码](https://raw.githubusercontent.com/chromium/chromium/main/sql/meta_table.h)，[HistoryDatabase 源码](https://raw.githubusercontent.com/chromium/chromium/main/components/history/core/browser/history_database.cc)。

适用：采用这两个数的职责划分。不能照搬其某些数据库的 raze（清空重建）辅助机制，ClipClop 的历史和收藏是用户数据。

### Zotero：升级前备份，不能兼容时明确要求升级

Zotero 官方说明多数版本维持数据库兼容，但某些变化需要打破兼容；旧程序打开新版库时给出版本错误。其文档提供从升级时自动备份恢复的方法，并解释未同步的新数据需要另行保留。[版本错误说明](https://www.zotero.org/support/kb/newer_db_version)，[升级备份恢复说明](https://www.zotero.org/support/zotero_data#restoring_from_the_last_upgrade_backup)。

适用：迁移前快照和明确恢复流程。ClipClop 是本地优先，不能采用“删掉本地库再从云端同步”的恢复假设。恢复旧快照也会回退备份后的新增历史、收藏及设置，必须明确展示时间点。

### Firefox：将降级视为数据保护问题

Firefox 对用新版打开过的 profile 提供降级保护，官方说明旧版可能损坏书签、历史等资料；它还采用按安装分配 profile 的策略。[Mozilla 官方说明](https://support.mozilla.org/en-US/kb/dedicated-profiles-firefox-installation)。

适用：不能证明兼容时保护原数据、给出可见说明。根据本次范围，不采用其 profile 隔离策略。

### Joplin：明确拒绝未知 profile 版本

Joplin 的数据库升级实现遇到不在已知版本列表中的 profile 版本会停止迁移，错误中包含程序版本、实际版本和预期版本，并建议升级。[JoplinDatabase 源码](https://raw.githubusercontent.com/laurent22/joplin/dev/packages/lib/JoplinDatabase.ts)。

适用：异常分级、诊断信息与不擅自降级。其严格策略可保护数据，但 ClipClop 可以通过 Chromium 式兼容协议减少无必要的阻断。

这些软件的共同点不是“无条件忽略未知字段”，而是明确何时可以继续、何时停止，以及如何保留和恢复数据。上面是具体模块/文档的行为，不代表所有产品、所有数据库都使用同一策略。源码引用为研究当日的 main/dev 分支，后续可能变化。

## 3. 推荐的兼容协议

### 两个版本数足够

- `PRAGMA user_version`：保留为 schema 迁移序号，只由升级迁移递增；不要修改 SQLite 自己的 `schema_version`。
- 独立且结构稳定的 `db_meta` 表记录 `min_compatible_version`：能够安全执行正常读写及清理的最低程序存储版本。它不是 App SemVer，也不进入用户设置表单。
- 程序内使用自身 schema 版本作为能力基线。暂不增加读版本、写版本、特性位图、迁移插件或完整 schema 指纹体系。
- 最低兼容版本必须是有效整数，不高于实际 schema 版本；正常迁移不得偷偷降低已有门槛。未知/异常元数据不能默认成兼容。

例如首个采用协议的版本为 schema 10，门槛为 10；未来 schema 11 只增加真正可选的元数据，则门槛仍为 10，schema 10 程序可正常启动且不把 11 改回 10。未来 schema 12 改变自动删除含义，则门槛提高到 12，schema 10/11 程序进入升级提示。

这是建议编号，并非已实施。首次引入协议的 schema 10 不会让现有 0.11.1/schema 9 二进制自动获得协议支持，也不会恢复 0.10.0；发布说明必须明确这个一次性兼容边界。

### 兼容声明的评审规则

| 变化 | 默认判断 | 需要验证 |
| --- | --- | --- |
| 新增可空或有合理默认值的普通列 | 可能兼容 | 旧 INSERT、UPDATE、DELETE 和新业务不变量均成立 |
| 增加索引 | 通常兼容 | UNIQUE 等新增约束不是单纯性能优化；旧写入可能失败 |
| 新增独立表 | 可能兼容 | 没有要求旧程序同步维护该表的派生数据或生命周期 |
| 新增必填无默认列、删除/改名列 | 不兼容 | 需要保留旧表示的过渡迁移，或提高门槛 |
| 增加 CHECK、外键、触发器 | 需重新评估 | 旧写入是否被拒绝、级联删除是否改变含义 |
| 新内容类型、已知字段的新枚举值 | 默认不兼容，除非提前设计容错 | Rust 解析、UI 呈现、复制粘贴与清理是否支持 |
| 收藏、固定、保留策略等保护语义 | 业务不兼容 | 旧清理必须遵守新保护规则，否则提高门槛 |
| FTS tokenizer、格式或必要扩展变化 | 需重新评估 | 旧运行时能否加载、搜索语义及写入一致性 |

运行时检查 required tables/columns、必要主键/约束及关键查询可准备性，用于发现结构不符；由兼容协议与跨版本测试证明业务安全。不要做“探测每一条任意未来 SQL 就自动放行”的机制，也不要在正常启动时模拟真实 INSERT 后回滚来猜兼容。

### 旧数据库的接入

- 对明确支持的历史 schema 4～9走固定迁移，再加入协议元数据。
- 不带协议元数据的未知高版本：不猜测、不迁移、不降号，展示升级/诊断入口。
- `user_version=0` 且没有用户 schema 对象才是新库；有表时归为旧式/异常结构，不能继续 CREATE 或覆盖，也不能往误选的其他软件数据库添加应用表。只对有证据的历史形态提供专门修复。
- 本地最早发布标签 v0.1.0 已使用 schema 4；已检查全部本地 v* 标签，未发现使用 schema 1～3的发布标签。因此以 4 为支持起点，不为没有发布证据的开发结构编造迁移；仍保留解释和恢复入口，不能提示直接删库。此检查不是远端所有历史制品的完整审计。
- 不为未来结构提供自动向下迁移；字段重命名优先阶段性新增并保留旧字段，但只有实际需要回退支持时才增加双写。

## 4. 迁移、锁与备份

推荐启动顺序：初始化最小日志和单实例机制 → 获取同数据目录生命周期锁 → 打开并识别数据库 → 兼容检查 → 需要升级时完成并验证快照 → 开始 IMMEDIATE 事务并重新检查版本 → 顺序迁移、设置迁移、写元数据、验证 → 一次提交 → 启动托盘、捕获、清理及普通界面。

### 原子性

新库创建及整条升级链由外层事务统一拥有，迁移函数不再各自嵌套开事务。使用 `BEGIN IMMEDIATE` 及有限锁等待，写入锁内重新读取版本，避免等锁后按旧版本重复 ALTER。SQLITE_BUSY 是可恢复的占用情况，不是数据库损坏。[SQLite 事务说明](https://sqlite.org/lang_transaction.html)。

这次事务范围仅包括可事务化的 SQL 和设置数据迁移；WAL 模式切换、备份、文件系统操作不塞进迁移事务。未来有文件迁移时必须另行设计恢复协议，不能靠 SQLite rollback 假装可以回滚文件。

升级前检查和升级后检查配合：`quick_check` 不验证所有索引/唯一约束；外键需要 `foreign_key_check`，FTS 要单独验证。普通无升级启动只做轻量版本/结构检查，完整扫描放在迁移、恢复及诊断场景。[SQLite PRAGMA 文档](https://sqlite.org/pragma.html#pragma_quick_check)，[FTS5 integrity-check](https://sqlite.org/fts5.html#the_integrity_check_command)。

### 并发

不隔离目录时，需要防止两个不同版本同时管理同一个库。复用现有 single-instance 插件负责唤醒窗口，再以数据目录内 OS 文件锁保证同一时刻一个应用拥有该数据目录；锁失败显示占用状态，不删除锁文件来“解锁”。进程退出由 OS 释放锁，锁文件存在不代表锁被占用。

生命周期锁解决新版本运行期间旧逻辑继续写的问题；迁移事务解决数据库层原子性，两者职责不同。设置读改写也应有 SQL 事务边界。旧二进制不认识新增文件锁，不能承诺与它并发运行安全：首次更新要退出已有实例，同目录 dev/正式版仍然顺序使用。外部 SQLite 工具不遵守应用锁也是支持边界，必要时提示关闭工具；不能声称文件锁防住一切外部写入。

### 迁移前备份

- 只在真实升级已有库前生成快照，不在每次启动备份。
- 使用 SQLite Online Backup API；rusqlite 已有对应可选 feature，启用现有依赖能力即可，无需引入 ORM 或迁移框架。[SQLite Backup API](https://sqlite.org/backup.html)。
- 不能直接复制正在使用的单个 `.db`：WAL 中可能还有已提交数据。WAL 是持久数据的一部分，不能随意删除。[SQLite WAL 文档](https://sqlite.org/wal.html#the_wal_file)。
- 持有应用目录锁，捕获尚未启动时制作快照。快照先写唯一临时目标，关闭并校验后标记完成；半成品不进入恢复列表。具体落盘及重命名在 macOS/Windows 分别验证。
- 记录原 schema、目标 schema、程序版本、时间；备份失败（空间、权限、忙、校验失败）则不开始迁移。迁移失败保留原库和已完成备份。
- 建议保留最近两份已验证迁移备份；重复失败不能淘汰唯一有效备份，只有新备份完成后才轮替。备份权限与数据目录一致，不上传剪贴板内容；备份会延长已删除内容的留存，需在存储说明中明确，提供手动清理入口。
- 恢复时先保留当前库的可恢复副本，关闭所有连接和实例，正确处理数据库与 WAL/SHM 整体状态，验证选中的备份，失败回到当前库。不能直接用旧 `.db` 覆盖仍然打开的数据库。
- 当前捕获把 flavor payload 存在库内，预览缓存可重建；复制文件条目记录的外部原文件并不包含在数据库快照里。未来启用 blob_path 外置存储时，备份范围必须一起升级。

## 5. 设置与单条坏数据

### 设置

保留现有 `Settings.extra` 和默认值机制，补齐真正的边界：

1. 完整表单保存时保留数据库最新 extra，不让旧快照覆盖未知字段；当前程序不应从 UI 接收并修改自己不理解的 extra。
2. 内部仅修改一个字段的路径继续读改写；整个过程置于事务中。显式区分“缺失”与 `null`，当前 `null` 表示无限保留，不能用默认 30 天替换它。
3. 区分持久化读取与用户输入校验。UI/IPC 输入继续严格；已存的未知 theme/language 等展示偏好可在运行时降级到 system，并保留原始值，不因无关字段保存而写回默认值。
4. 未知或损坏的 retention/history_limit 不猜测为默认删除策略，先暂停自动清理并提示修复。不能用整个 Settings::default() 覆盖解析失败的对象。
5. 对已知旧格式做明确设置迁移；新枚举值若没有上述保留机制就算兼容边界变化。未知字段的 round-trip 测试不能证明已知字段未知值也能 round-trip。

不需要写任意层级 JSON 合并框架。当前设置是扁平对象，围绕应用设置实现保留原始值与只更新明确字段即可。

### 历史记录

未知类型默认由兼容门槛拦截。若未来要支持新类型在旧程序显示，应先发布“未知条目”表示，再发布新类型；不能直接当 text 自动粘贴。

单条损坏记录应提供可见的受损占位/诊断，不让一条坏 metadata 使所有历史不可访问。保留原行，禁用无法安全执行的预览和粘贴，不静默跳过造成分页和数量错位。这个改动涉及查询 DTO 和前端，不是把 `collect<Result<...>>` 改成过滤错误就完成。

FTS 是可重建派生数据；确认主记录健康后可以有明确重建流程。不能在未知版本或无法读取核心数据时“删 FTS 试试”。

## 6. 用户可见的失败与恢复

第一阶段必须让应用能显示独立于数据库服务的启动错误界面。兼容时进入完整 app；不兼容时进入解释和恢复入口，不能把一个空数据库伪装成历史已清空。

| 失败类型 | 展示与行为 |
| --- | --- |
| 数据库需要更新程序 | 展示应用版本/所需版本信息，提供下载兼容版本、打开日志/数据位置、退出 |
| 数据目录被占用 | 提示关闭另一实例或稍后重试；不运行迁移和清理 |
| 磁盘空间或权限问题 | 明确问题，允许修正后重试；不称为损坏 |
| 迁移失败 | 保留数据库，显示失败阶段及备份入口；不自动恢复旧快照 |
| 结构异常/损坏 | 提供诊断与经过验证的恢复流程；不自动删库 |
| 单个设置异常 | 非破坏性降级，自动清理保持关闭直到策略有效 |

启动错误界面只依赖最小状态；正常 IPC 不能在 AppState 尚未初始化时被调用。启动错误不能继续用 `?` 传入已知会 abort 的 setup 路径。日志记录版本、迁移步骤、SQLite 错误码、备份状态和耗时，不记录剪贴板正文/设置完整内容。

暂不实现“任意未来数据库的只读浏览器”。当前复制也会更新使用时间，普通页面会加载设置、查询和注册服务；仅加 query_only 无法得到完整安全的只读模式。先完成错误/恢复壳，再根据确切需求增加版本化只读导出。下载兼容应用的入口不得依赖正常 SettingsService 已成功启动。

## 7. 测试与发布门槛

| 场景 | 必须满足 |
| --- | --- |
| 真正空库 | 建表、版本、协议元数据一次提交 |
| schema 4/5/6/7/8/9升级 | 历史、payload、时间、收藏、设置保留；搜索结果可用 |
| 兼容未来库 | 旧基线程序可捕获、查询、复制、保存设置；未知字段和值保留，schema不倒退 |
| 不兼容未来库 | 不启动写入/捕获/清理；可见升级提示 |
| 多列、少列、额外 NOT NULL/UNIQUE/CHECK/触发器 | 不误判为兼容；不靠任意补列修复 |
| 收藏及后续保护语义 | 跨版本自动保留和清空均不误删 |
| 设置未知字段、未知枚举、旧表单、null、损坏策略 | 未知内容保留；清理策略不能意外变得更激进 |
| 迁移中故意失败/进程终止 | 重开后原状态或完整新状态，schema 与数据一致 |
| 两进程同时启动/迁移 | 仅一个应用拥有目录，等待者不按旧版本重复迁移 |
| WAL 有未 checkpoint 数据时备份 | 恢复后包含已提交数据与 payload |
| 备份空间不足/权限拒绝/半成品 | 不开始迁移，已有有效备份不丢失 |
| 恢复失败/应用重启 | 当前数据仍可取回；不混用旧 WAL |
| 单条坏数据/FTS 故障 | 不静默丢记录，诊断清晰，必要恢复不影响主数据 |

使用固定历史版本 schema 或脱敏合成 fixture，不从当前 schema 删除字段冒充全部历史版本。比较业务结果和规范化必需结构，允许历史 CHECK 文本、列顺序和默认表达式的合理差异。测试复用现有 Rust/前端框架，macOS 与 Windows Quality 都跑；不新增测试框架。

兼容声明需要固定的旧基线存储实现执行“新版建库 → 旧基线读写 → 新版再读”的往返测试。只把 user_version 人为调大能测到版本分支，不能替代真正跨版本测试。每次迁移 PR 必须说明旧读写、清理、设置、备份恢复影响；已发布迁移不随意改写，以新迁移修正实际旧库。

## 8. 实施顺序与范围

**第一批，一起构成可发布的可靠基线：**

- 兼容协议、历史库接入、明确错误分类。
- 原子新建/整链迁移，迁移前有效备份，目录锁和锁超时处理。
- 不依赖数据库的启动错误界面与可操作的备份恢复入口。
- 设置未知字段保存修正；启动设置失败的安全处理，自动删除默认关闭。
- 真实历史 fixture、兼容/不兼容往返和中断/备份测试。

**第二批，继续完善数据可用性：**

- 单条受损数据的占位呈现与安全操作限制。
- 明确的 FTS 诊断/重建入口。
- 根据第一批跨版本用例进一步完善未知枚举的逐字段保留与编辑体验。

第二批完成前，新内容类型/不支持的枚举仍提高兼容门槛，不通过“兼容”声明绕过未完成能力。

暂不做目录隔离、任意未来 schema 自动修复、自动降级、跨版本同时写库、迁移插件平台、每日备份调度、通用 JSON 合并引擎或通用只读数据库浏览器。
