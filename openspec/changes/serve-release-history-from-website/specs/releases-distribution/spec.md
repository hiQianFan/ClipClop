## ADDED Requirements

### Requirement: Centralized releases production

The release pipeline SHALL generate a public `releases.json` file using authenticated GitHub API access in CI. It SHALL include all published non-draft, non-prerelease releases in deterministic publication order, with the newest entry marked latest, and SHALL NOT expose credentials to consumers.

#### Scenario: Initial backfill

- **WHEN** synchronization runs before any `releases.json` exists
- **THEN** it retrieves all GitHub pages within the documented safety limits and produces one complete releases JSON document
- **AND** an incomplete retrieval does not publish a partial index

#### Scenario: Release publication and subsequent edits

- **WHEN** the existing pipeline successfully publishes a release
- **THEN** it explicitly invokes the shared synchronization workflow without relying solely on release events generated by GITHUB_TOKEN
- **AND** manual and six-hour scheduled synchronization support later edits and withdrawals

### Requirement: Failed synchronization preserves usable data

The producer SHALL validate generated data before replacing the mutable releases file. Failed synchronization SHALL NOT modify updater manifests, download assets, or the previous successful releases file.

#### Scenario: Upload or validation fails

- **WHEN** generated data cannot be uploaded or validated
- **THEN** clients continue to resolve the previous successful JSON
- **AND** the CI job reports failure with diagnostic context without secrets

#### Scenario: Upstream data is unchanged

- **WHEN** normalized release content matches the current content hash
- **THEN** synchronization does not replace the index solely because the current time changed

### Requirement: Complete releases file

The website SHALL provide `/releases.json` containing the complete releases list. The response SHALL include schemaVersion, contentHash, generatedAt, total, and releases.

#### Scenario: App displays releases incrementally

- **WHEN** the App loads `releases.json`
- **THEN** it can show the first ten entries and reveal more entries locally without additional network release-page requests

#### Scenario: No published releases exist

- **WHEN** a complete successful synchronization returns zero formal releases
- **THEN** the index is valid with an empty releases array and total zero
- **AND** a failed fetch is not represented as this successful empty result

### Requirement: Website read-only distribution

The website Worker SHALL serve `releases.json` exclusively from the existing R2 binding without runtime GitHub access. It SHALL support GET, HEAD, and OPTIONS, enforce the fixed file path, and return JSON errors with appropriate status codes rather than HTML fallback pages.

#### Scenario: Desktop cross-origin request

- **WHEN** a production desktop WebView requests a valid API object
- **THEN** CSP permits the website origin and the response permits non-credentialed cross-origin reading
- **AND** equivalent CORS headers are present on error and preflight responses

#### Scenario: Invalid or unavailable resource

- **WHEN** a request attempts an unsupported path, a missing object, or an unavailable R2 read
- **THEN** the Worker rejects invalid paths, returns 404 for missing objects or 503 for unavailable storage, and does not cache the error

### Requirement: Explicit caching contract

The website SHALL expose ETag and a maximum five-minute freshness lifetime for `releases.json`. The deployment SHALL explicitly enable and verify the intended edge caching. Clients SHALL reuse successful responses within a session and support revalidation on manual refresh.

#### Scenario: User refreshes version history

- **WHEN** the user requests a refresh
- **THEN** the client revalidates `releases.json`
- **AND** a late response from an older request cannot overwrite the current state

### Requirement: Safe release content

The producer SHALL retain bilingual Markdown and reject unsafe rendered HTML before publication. App consumers SHALL validate the versioned response before rendering, and SHALL fall back to Markdown text when rendered HTML fails the client safety check.

#### Scenario: Malicious or malformed content

- **WHEN** an upstream note includes scripts, event handlers, unsafe links, embedded frames, forms, or remote images
- **THEN** the unsafe rendered HTML is rejected or ignored
- **AND** malformed metadata cannot replace the active index

#### Scenario: Unexpected API schema

- **WHEN** the App receives an unsupported schema
- **THEN** it rejects the result as a recoverable loading error and does not update its successful cache

### Requirement: Shared consumer source with recoverable loading states

The App and website changelog SHALL retrieve releases from `releases.json` without automatic GitHub fallback. The website home page SHALL use the releases file for latest stable version text, and the website header SHALL not request GitHub stars at runtime. App incremental display SHALL preserve selection and existing content on refresh failure. Requests SHALL time out within fifteen seconds.

#### Scenario: First load fails

- **WHEN** no history has loaded and the website request fails or times out
- **THEN** the App shows a centered explanation and retry button instead of an indefinite skeleton
- **AND** skeletons appear only during an active initial load or retry

#### Scenario: Refresh fails after content exists

- **WHEN** refreshing `releases.json` fails
- **THEN** existing history, selection, and detail remain available and a localized retry action is shown

#### Scenario: Website changelog uses migrated data

- **WHEN** a visitor opens either language's changelog
- **THEN** the page reads the same versioned API, preserves language-specific notes and cached-content fallback, and reveals additional releases locally on demand

#### Scenario: Website home uses migrated latest release

- **WHEN** a visitor opens the home page
- **THEN** stable version text uses the newest release from `releases.json` or cached/default local content
- **AND** it does not request GitHub latest-release API

#### Scenario: No browser-side GitHub API calls remain

- **WHEN** the production website renders home, changelog, and shared header
- **THEN** client-side scripts do not request GitHub repository or releases APIs
- **AND** the shared header does not fetch GitHub stars at runtime

### Requirement: Independent updater and compatible rollout

The migration SHALL preserve `/latest.json`, `/download/*`, immutable installer paths, and existing signature verification. Public API deployment and backfill SHALL precede consumer release. Rollback SHALL preserve the v1 API contract for already-updated clients.

#### Scenario: Feed synchronization fails after an App release

- **WHEN** a release is already public but history synchronization fails
- **THEN** downloads and automatic updates remain usable and the releases endpoint retains the previous successful JSON
